# BabyLM 1000 萬字：真實文字計畫（2026-11-08，在任何結果之前寫下）

**Gary 的決定（2026-11-08）：** 用 BabyLM 2026 Strict-Small（1000 萬字），tokenizer 用 2026 Strict-Small 官方那套
（理由見 `babylm-tokenizer.md`）。pod 照建議：要跑才開，跑完就刪（GPU pod 最多活 6 小時，Job 不能 sleep）。

前提：合成任務做完了（`memory-plan.md`）。在練過的距離內，統一版和分開版打平；
但如果中間有會干擾的雜訊，到了沒練過的長距離，統一版會被雜訊寫入稀釋，掉得比分開版多。

## 0. 要回答的問題

1. **學得起來嗎：** 統一版在真實文字上，跟同參數的 Transformer 差多少。
2. **共用有沒有代價：** 統一版對分開版 P-free（同寬度，P-free 多一組位址，參數多 23%）。
3. **長距離：** 這是合成任務那個發現在真實文字上的版本。真實文字裡每個 token 都會寫進記憶，
   大部分跟後面要預測的東西無關。所以要看：越後面的位置、以及超過訓練長度（512）以後，
   統一版是不是比分開版退得多。

## 1. 資料

- `BabyLM-community/BabyLM-2026-Strict-Small`：6 個來源檔（CHILDES、Gutenberg、OpenSubtitles、Simple Wiki、BNC spoken、Switchboard），
  每個檔都是一整段連續文字，沒有分篇。
- 每個來源最後 2% 的行留作驗證集，其餘訓練。
  - 訓練：9,807,510 字，15,174,250 個 token。平均一個字 1.55 個 token。
  - 驗證：192,490 字，297,339 個 token。
- 每一段編成 `<s> 文字 </s>`，依固定順序接起來。訓練時切成不重疊的 513 個 token 窗口，每一輪每個窗口用一次，順序打亂。
- 練 10 輪，共看 9,810 萬字，在 BabyLM「最多看 1 億字」的規則內。
- 程式在 `scripts/babylm/babylm.py`，產生的檔案在 `data/babylm10m/`（gitignored）。

## 2. 模型

三個模型都是 12 個 block、寬度 288、詞表 16384，embedding 和輸出共用。

- **統一版 S**：每個 block 712 格，共 10,669,944 個參數。
- **分開版 P-free**：每個 block 712 個固定知識格，加上 712 個上下文格，兩組位址分開，共 13,139,172 個參數。
- **Transformer T**：llama2.c 15M 的配置，共 10,694,304 個參數，跟 S 差 0.2%。
  - 6 層，每層一個 attention block 加一個 SwiGLU block（768 個隱藏單元）。
  - 6 個頭、每頭 48 維，用 RoPE。
  - 程式在 `scripts/variants.py` 的 T。

## 3. 訓練

三個模型設定完全一樣：1 個 seed（1337）、1 個學習率，不掃參數。

- 序列長 512，batch 64，每步 32,768 個 token。共 4,630 步，等於 10 輪。
- 學習率 1e-3（跟記憶實驗相同）。前 200 步線性 warmup，之後 cosine 降到 0。
- AdamW：betas (0.9, 0.95)，weight decay 0.1，grad clip 1.0，dropout 0。
- bf16 加 `torch.compile`。
- 計畫：`scripts/nrp/babylm.txt`，3 行。跑在單卡 A6000 bare pod 上，跑完就刪。
- 粗估每個 run 15–30 分鐘，全部約 1 個 GPU 小時。

## 4. 量什麼

評測程式是 `scripts/babylm/eval_babylm.py`，用 fp32，看最後一步的權重（不是驗證集最好的那一步）。

- **驗證 loss（每個 token 的 nats）@512：**
  - 驗證文字依序切成 580 個 512 長的窗口，全部都算。
  - 給整體平均，也給位置 0–64、64–128、128–256、256–512 各一段的平均。
- **驗證 loss @2048：**
  - 145 個 2048 長的窗口。除了上面的分段，再加 512–1024、1024–2048 兩段。
  - 只測 S 和 P-free。T 的 RoPE 在 512 以後的位置沒練過，測了也沒意義。
- **BLiMP：**
  - 完整 67 組文法測驗，每組 1000 對句子，資料是 `nyu-mll/blimp`，不是 BabyLM 篩過的版本。
  - 一句話的分數是前面加 `<s>` 之後，每個 token 的 log 機率加總。好句分數高於壞句才算對。
  - 給整體正確率，也按領域和現象分開列。
- **檢查：** 評測算出的 @512 整體 loss，應該跟 `train.py` 最後一次的驗證 loss 相差 0.01 以內
  （`train.py` 用 bf16，看 580 個窗口裡的 576 個）。差太多就是評測寫錯，先修再判讀。

## 5. 判讀規則

只有 1 個 seed，所以先定好什麼程度算「打平」：

- 驗證 loss 差距小於 0.02 nats 算打平，約為預期 loss 的 0.5%。
- BLiMP 差距小於 2 個百分點算打平。

1. **學得起來嗎（S 對 T）：** 用 @512 整體 loss 和 BLiMP 整體正確率，各自歸為「打平」「S 較好」「S 較差」，並寫出差多少。
2. **共用的代價（S 對 P-free）：** 同樣的規則。
3. **長距離（用 @2048 的窗口）：**
   - 每一段位置算 d＝S 的 loss 減 P-free 的 loss。
   - 如果 d(1024–2048) − d(256–512) ≥ 0.02，就說「統一版在超過訓練長度以後退得比較多」。
   - 如果 ≤ −0.02，就說「統一版退得比較少」。介於兩者之間算打平。
   - 每個模型自己的 loss(1024–2048) − loss(256–512) 也列出來：正數表示超過訓練長度以後變差。

## 6. 事前預測

- **S 對 T：** S 的 loss 比 T 高 0.02–0.10，也就是 T 略好。BLiMP 打平。
- **S 對 P-free：** P-free 的 loss 低不到 0.05（它參數多）。BLiMP 打平。
- **長距離：**
  - 在 0–512 內，d 大致不變。
  - 超過 512 以後 d 變大至少 0.02，也就是統一版退得比較多，跟合成任務一致。
  - 兩個模型自己的 loss(1024–2048) 都在各自 loss(256–512) 的 0.05 以內，不會因為超過長度就崩。

## 7. 這次不做

- **藏密碼再問（passkey）：** 1000 萬字、1000 萬參數的模型預期完全做不到，全是 0 看不出差別。

- **官方 GPT-2 baseline 當參考：** 它有 1 億參數，而且在完整訓練集上練過，包含我們的驗證段，loss 不能比。

## 9. 查分開版超過訓練長度為什麼崩（2026-11-08，在任何診斷結果之前寫下）

Gary 要先查第 8 節的 P-free：它在位置 1024–2048 的 loss 比自己在 256–512 時高 0.90，S 只高 0.04。
用 Mac 上第 8 節最後一步的權重，在 145 個 2048 長的驗證窗口上逐層重算記憶（dense 形式，CPU），只在測試時改記憶，不重新訓練。
程式是 `scripts/babylm/diag_length.py`。

**為什麼懷疑記憶：** 模型裡只有記憶跟位置有關。conv 只看前 4 個 token，也沒有位置編碼。
兩個模型的記憶公式一樣，每個格子的證據 E 都是「過去寫入的衰減加總」，都會隨位置變大，
時間常數是幾百個 token（第 8 節）。差別在讀出的組法：
- **S：** 每個格子的讀出是 (w·μ + 上下文的值) / (w + E)，也就是固定知識 μ 跟上下文的值的加權平均。E 變大時，上下文取代固定知識，總量不變。
- **P-free：** 上下文讀出是 (上下文的值) / (w + E)，等於一個先驗是 0 的平均，再加在另外算的固定知識上。E 變大時，上下文那一項變大，固定知識那一項不變。

**兩種介入（只影響位置 512 以後，512 以前不變）：**
- **window：** 每個格子只記最近 512 個寫入。這測的是「超過 512 以前的歷史」本身。
- **clamp：** 全部歷史都留著，但每個格子的 E 封頂在它在這個窗口前 512 個位置內到過的最大值，存的值也按同一個比例縮。
  讀出內容的平均不變，只是把「上下文佔多少份量」限制在練過的範圍。這測的是「份量變大」。

**檢查：** 逐層重算要跟模型本身的輸出一致（相對誤差小於 1e-5，已確認：S 6.4e-7，P-free 8.3e-7）。
normal 的分段 loss 要跟第 8 節 GPU 評測的數字相差 0.005 以內，不然先查原因再判讀。

**判讀規則：**（P-free 自己 normal 時 256–512 的 loss 約 3.26，記為 base）
1. **window（所有 block）：** P-free 的 1024–2048 回到 base＋0.05 以內，就說「崩掉來自 512 以前的歷史」。
2. **clamp（所有 block）：** 也回到 base＋0.05 以內，就說「崩掉來自上下文讀出的份量超出練過的範圍，不是舊 token 的內容」。
   如果 window 救得回來、clamp 救不回來，就說「是舊內容本身，不是份量」。
3. **機制的描述（不做判定）：** 每個 block 在 256–512 和 1024–2048 的上下文份量 Σ r·E/(w+E) / Σ r，
   以及兩個讀出項（固定知識、上下文）和兩者加總的 RMS，S 和 P-free 並排列出。
4. **哪幾層（P-free，只對一個 block 做 window，12 次）：** 列出單獨修一層就能救回至少一半差距的 block。
   差距指 normal 1024–2048 減 base。
5. **S 的對照：** window、clamp 對 S 的 1024–2048 影響有多大，照實列出。

**事前預測：**
- window 和 clamp 都能把 P-free 救回 base＋0.05 以內。也就是份量是原因，不是舊內容。
- P-free 的上下文讀出 RMS 在 1024–2048 比 256–512 明顯變大，固定知識那一項不變，所以 block 輸出變大。
  S 的上下文份量也會變大，但 block 輸出的 RMS 大致不變，因為上下文取代了固定知識。
- 單獨修一層就能救回一半以上的 block 有 1–3 個，而且在時間常數最長的幾個裡面（block 4 是 602，block 8 是 543，block 11 是 541）。
- window 和 clamp 讓 S 的 1024–2048 變動不到 0.05。

## 10. 崩掉原因的診斷結果（2026-11-08）

程式是 f8686d7，結果在 `babylm/diag_length.{json,log}`，用 145 個 2048 長的窗口，在 Mac 的 CPU 上跑，共 15 分鐘。

**檢查：**
- 逐層重算跟模型本身一致：相對誤差 S 6.4e-7、P-free 8.3e-7。
- normal 的分段 loss 跟第 8 節 GPU 評測一致：S 1024–2048 是 3.3193 對 3.3193，P-free 是 4.1600 對 4.1596。

**位置 1024–2048 的 loss**（P-free 的 base，也就是它自己 normal 時 256–512 的 loss，是 3.260，normal 崩到 4.160，差距 0.900）：

| | normal | window（只記最近 512 個寫入） | clamp（份量封頂在練過的範圍） |
|---|---|---|---|
| P-free | 4.160 | 3.531（救回 70%） | 3.350（救回 90%） |
| S | 3.319 | 3.300 | 3.323 |

**單獨對 P-free 一個 block 做 window，救回差距的比例：**
- block 0：36%
- block 2：16%
- block 5：6%
- block 4：5%
- block 8：4%
- 其他 block：−1% 到 1%

12 個 block 加起來約 72%，跟所有 block 一起做 window 的 70% 差不多。

**每個 block 的上下文份量 Σ r·E/(w+E) / Σ r，從 256–512 到 1024–2048：**
- **P-free：**
  - 有 8 個 block 變成 1.6–2.7 倍：block 3 是 0.167→0.301，block 4 是 0.077→0.162，block 5 是 0.080→0.169，block 7 是 0.084→0.216，block 8 是 0.072→0.196。
  - 上下文讀出的 RMS 變成 1.2–3.6 倍，例如 block 5 是 0.014→0.051，block 7 是 0.017→0.054。
  - 固定知識讀出的 RMS 不變（0.013–0.024，變動不到 ±25%）。
  - 所以 block 輸出的 RMS 變成 1.0–2.4 倍。
- **S：**
  - 份量也變大，但只有 1.1–1.5 倍（多 0.01–0.04），例如 block 2 是 0.135→0.173，block 11 是 0.119→0.159。
  - block 輸出的 RMS 最多變大 24%（block 5 是 0.017→0.021）。
- clamp 讓 P-free 每個 block 的份量和 RMS 都回到 256–512 的水準（份量差 ±0.06 以內）。

**照第 9 節的規則判讀：**
1. **window：** 3.531，比 base 高 0.27，沒有回到 base＋0.05 以內。不能說「崩掉完全來自 512 以前的歷史」，只救回 70%。
2. **clamp：** 3.350，比 base 高 0.09，也沒有回到 base＋0.05 以內，但救回 90%，是兩種介入裡最強的。
   「window 救得回、clamp 救不回」的情況也沒有發生，所以不支持「是舊內容本身」。
   結論是：**崩掉大部分（90%）來自上下文讀出的份量超出練過的範圍**，剩下 0.09 沒有解釋到，這也沒有達到事先訂的門檻。
3. **機制：** P-free 過了 512 以後，上下文讀出的份量在多數 block 變成約 2 倍。這一項是加在不會變小的固定知識上的，
   所以 block 輸出最多變大 2.4 倍，進到訓練時沒見過的範圍。S 的份量只增加 1.1–1.5 倍，block 輸出最多增加 24%。
4. **哪幾層：** 沒有任何一個 block 單獨修就能救回一半。最多的是 block 0（36%），時間常數最長的 block 4、8、11 只有 5%、4%、0%。
   傷害分散在很多層，而且越前面的 block 影響越大。可能是前面 block 的輸出變了，改變了後面每一層的位址，一路往下放大。

## 13. 探索：超過訓練長度的幾個追問（2026-11-08，沒有事先寫規則，只是觀察）

程式是 `scripts/babylm/explore_length.py`、`explore_context.py`、`explore_t_long.py`，彙整用 `summarize_explore.py`。
seed 0 的結果在 `babylm/explore/`，seed 1、2 的在 `babylm_seeds/`（`explore_seed*.json`、`context_*.json`），彙整在 `babylm_seeds/explore_summary.json`。
全部在 Mac 的 CPU 上跑，共約 1.5 小時。

**A. Transformer 超過訓練長度：**
- seed 0：位置 256–512 是 3.155，512–1024 是 4.011，1024–2048 是 4.527，多了 1.37。seed 1、2 多 1.40、1.26（`babylm_seeds/t_long_seed*.json`）。
- 所以在 1024–2048，seed 0 的三個模型是 S 3.319、P-free 4.160、T 4.527，只有 S 撐得住。

**B. 同一批 token，上下文變長是幫忙還是拖累？**
- **做法：**
  - 每個驗證 token 算兩次 loss：一次在 512 長的窗口裡，一次在長窗口（2048 或 8192）裡。
  - 只比在 512 窗口裡位於第 256–511 個位置的 token，所以短的那次也至少有 256 個 token 的上下文。
  - 差值是「長的 loss 減短的 loss」，正數表示更長的上下文反而更差。
- **檢查：** 在長窗口的 256–512 段，兩次的上下文完全一樣，所有模型、所有 seed 的差值都是 0.0000。
- **結果**（seed 0／1／2）：

| 長窗口裡的位置 | 512–1024 | 1024–2048 | 4096–8192（8192 長窗口） |
|---|---|---|---|
| S | +0.021／+0.021／+0.025 | +0.044／+0.074／+0.062 | +0.060／+0.131／+0.093 |
| P-free | +0.18／+0.39／+0.25 | +1.04／+3.29／+2.46 | +2.75／+4.81／+4.82 |
| T | +1.20／+1.22／+1.09 | +1.39／+1.43／+1.29 | +1.61／+1.65／+1.60 |

- **意思：**
  - 三個模型都沒有從 512 以外的上下文得到好處。
  - S 只是慢慢變差：到 16 倍訓練長度多 0.06–0.13。
  - P-free 和 T 一過 512 就崩。
  - 所以「S 撐得住」是指它不會壞，不是指它用上了更長的上下文。

**C. 更長的窗口（seed 0，各自窗口裡的分段 loss）：**
- 8192 長的窗口：
  - S 在 256–512 是 3.256，4096–8192 是 3.350（多 0.09），2048 以後就不再變差。
  - P-free 在 4096–8192 是 6.03（多 2.80）。
- P-free 加 clamp 後，4096–8192 是 3.377（多 0.14），跟 S 只差 0.03。S 加 clamp 幾乎不變（3.353）。
- 4096 長的窗口也一樣：S 在 2048–4096 多 0.08，P-free 多 2.22，P-free 加 clamp 多 0.11。

**D. 為什麼 S 的份量長得比較少（第 10 節留下的問題）：**
- **做法：** 每個 block 用它真正的輸入，重算它在 1024–2048 和 256–512 的上下文份量，取 12 個 block 增長倍數的中位數。分兩個條件：
  - **時間常數：** 用自己的，或換成另一個模型同一層的。
  - **往下傳的部分：** 讓前面的 block 照常跑（normal），或者全部加 clamp，讓每個 block 收到的輸入都維持在練過的範圍（記為「不往下傳」）。

| seed | S | S 換成 P-free 的時間常數 | P-free | P-free 不往下傳 | P-free 不往下傳＋換成 S 的時間常數 |
|---|---|---|---|---|---|
| 0 | 1.30 | 1.43 | 1.71 | 1.56 | 1.40 |
| 1 | 1.28 | 1.44 | 2.28 | 1.51 | 1.35 |
| 2 | 1.34 | 1.49 | 1.84 | 1.51 | 1.42 |

- **粗估拆解：** 把 P-free 比 S 多長的部分（0.41／1.00／0.50）拆成三塊：
  - **往下傳：** 38%／77%／66%。前面 block 的輸出變大以後，後面 block 的位址跟著變，證據長得更多。
  - **時間常數：** 40%／16%／18%。P-free 的時間常數比較長，seed 0／1／2 分別是 233–602／250–747／242–652，S 是 229–449／225–572／231–451。
  - **剩下的：** 22%／6%／16%。兩個模型學到的位址本身不一樣。
  - 用的是中位數，拆的順序也會影響比例，所以只是粗估。
- **S 自己往下傳的部分很小：** S 不往下傳時是 1.28／1.27／1.31，跟照常跑只差 0.01–0.03。因為 S 的讀出是加權平均，份量變大時固定知識那一項跟著變小，block 輸出幾乎不變，就沒有東西往下放大。
- **結論（探索性）：**
  - 份量差別主要不是時間常數，而是 P-free 的上下文讀出加在固定知識上面：輸出變大，一層層往下放大。
  - 這就是第 9 節講的「讀出的組法」不同。時間常數只佔一小部分。
- **還沒做的：**
  - 用訓練去驗證，例如把兩個模型的時間常數固定成一樣再練。
  - S 那 0.04–0.13 的慢慢變差是從哪裡來的。clamp 救不了它，所以不是份量的問題。window 在 1024–2048 救回約一半（45–58%），
    所以有一部分來自 512 以前的舊內容。
