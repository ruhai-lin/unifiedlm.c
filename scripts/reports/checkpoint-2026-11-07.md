## 0. 結論

- **結構：** 統一 block 每層只算一次位址 r，同一個 r 同時給 FFN 那半（μ）和 attention 那半（狀態）用。
  分開的 block 要算兩次，每層多一個 d×m 的投影矩陣 K_f，其他完全一樣。
- **速度：** 逐 token 生成時，同寬度的分開版要花統一版 1.14–1.24 倍的時間（整個模型、4 種大小、兩次量測），
  也就是統一版每個 token 省 12–19%。只看 mixer 是 1.25–1.37 倍。實測倍數跟「每個 token 少搬多少記憶體」的計算對得上。
- **能學：** S 重現 README（100K 步 val 1.2911，README 1.2905）；學習率 2e-3 到 1.2716。
  越後面的 token loss 越低（1.49 → 1.26），狀態那半確實在讀前文。
- **代價：** 加速是同寬度比的，分開版因此多 35% 參數，學得比較好（20K 步 1.3033 對 1.3672，同為 lr 1e-3）。
  縮到同參數量的分開版速度跟 S 差不多（0.85–1.05 倍），但每一個學習率都學得比 S 差。

## 1. 主線（Gary 2026-11-07 決定）

## 2. 結構

### 2.1 統一 block（S）

程式在 `model.py:45-85`（`UnifiedBlock`），訓練用的 Triton kernel 在 `kernel.py`，推論在 `run.c`。每層、每個 token：

1. `h = RMSNorm(x)`，`u = 因果 depthwise conv(h)`（寬度 4）
2. **位址** `r = relu²(K u + b) / (ε + Σ)`：長度 m 的向量，m 是槽數（260K 模型 m=140）。K 是 m×d。
3. **值** `v = W_v h`（W_v 是 d×d）
4. **狀態（取代 attention）：** 寫入 key 用上一個位址 `r_{t-1}`、value 用 `v`，每步乘衰減 λ。讀取用 `q = r / c`，
   c 是每個槽在前文被用了多少的累計加上先驗 w。
5. **μ（FFN）：** 讀 `μ (q·w)`，μ 是 d×m。前文常用的槽（c 大），μ 的份量變小，讓給狀態，這叫「耦合」。
6. 輸出 `x + μ(q·w) + 狀態讀出`。

統一的意思：**同一個 r 同時是 FFN 的隱藏層和 attention 的 key／query**，所以每層只有一個 K。

### 2.2 對照組（`scripts/variants.py`）

- **D**（`DecoupledBlock`，第 25 行）：一樣一個 r，但 μ 直接讀 `μ(r)`，不看 c。也是統一的，只是沒有耦合。
- **P(m_s, m_f)**（`SeparateBlock`，第 38 行）：兩條路各自有 K、各自有槽：`μ(r_s) + 狀態(r_f)`。
  - P-free = P(140,140)：兩邊都給滿，跟 S 同寬度。
  - P-eq = P(69,140)、P(93,93)、P(105,70)：槽數縮到跟 S 同參數量。
- **A(207,207)**：層與層輪流，一層只有狀態、下一層只有 μ，各 207 槽，跟 S 同參數量。

## 5. 速度

### 5.1 方法

- 程式：`scripts/bench/mixer_bench.c`，指令：`cc -O3 -ffast-math -mcpu=native -o mixer_bench scripts/bench/mixer_bench.c && ./mixer_bench`
- Mac mini M4（16 GB）、單執行緒、batch 1、fp32，每個配置計時至少 1.5 秒。權重是隨機數，因為速度只跟矩陣大小有關。
- 兩種範圍：
  - **只算 mixer：** 位址投影、μ 讀取、狀態更新和讀取，也就是各配置不同的部分。
  - **整個模型：** 每層再加 RMSNorm、conv、W_v、殘差，最後加 RMSNorm 和輸出層。260K 用 512 詞表，其他用 32K。
- 大小沿用 `docs/models.md` 的 260K / 15M / 42M / 110M（d、層數、m 對齊 llama2.c）。
- 每種配置都有幾種 C 寫法：S-merged（run.c 的合併 U）、S-split（分兩次掃）、S-fused（一次掃完），
  P-free 也有分兩次掃和一次掃完兩種。**比較時兩邊各取自己最快的寫法**，這樣差距只來自第二個 K。
- 跑兩次：`mixer-bench-m4.txt`、`mixer-bench-m4-run2.txt`。

|---|---|---|---|---|
| 260K | 1.21 | 1.21 | 1.25 | 1.26 |
| 15M | 1.14 | 1.15 | 1.32 | 1.31 |
| 42M | 1.24 | 1.21 | 1.35 | 1.37 |
| 110M | 1.22 | 1.22 | 1.33 | 1.30 |

統一版整個模型的絕對時間（第 1 次）：260K 23.3 µs、15M 1176 µs、42M 3836 µs、110M 10866 µs／token。

### 5.3 為什麼快：每個 token 搬的記憶體

權重讀一次，狀態讀一次、寫一次，fp32：

| 大小 | 統一（MB） | 分開（MB） | 搬動量倍數 | 實測倍數（第 1 次） |
|---|---|---|---|---|
| 260K | 1.74 | 2.10 | 1.21 | 1.21 |
| 15M | 80.3 | 90.1 | 1.12 | 1.14 |
| 42M | 250.3 | 292.2 | 1.17 | 1.24 |
| 110M | 719.2 | 860.1 | 1.20 | 1.22 |

15M 的倍數最小，因為 32K 詞表的輸出層占了統一版搬動量的 46%，兩邊一樣大。
110M 統一版約 66 GB/s，接近單核頻寬，所以速度由搬動量決定。只算 mixer 的搬動量倍數各大小都是 1.25，實測 1.25–1.35；
大一點的模型多出來的部分，來自分開版多算一次位址（relu² 和正規化）。

### 5.4 同參數量的分開版不比較慢

整個模型，S 為 1.00（第 1 次）：
- 260K：P(69,140) 1.02、P(93,93) 0.90、P(105,70) 0.85、A 0.92
- 15M：P(355,712) 1.05、P(474,474) 0.97、P(534,356) 0.92、A 0.99

所以加速只在「同寬度」下成立。同參數量時速度差不多，統一版的好處變成品質（第 6 節）。

### 5.5 GPU 訓練

A40、260K、batch 128，每步時間的中位數（`phase2a/*_lr1e-3/train.log`）：
S 45.9 ms、D 44.1、P-free 49.3（1.07 倍）、P(69,140) 46.1、P(93,93) 38.5、P(105,70) 34.3、A 35.7。
這麼小的模型在 GPU 上大部分時間花在啟動 kernel（MFU 1.8%），不能代表真正的差距。

### 5.6 限制

- 只量了 CPU 單執行緒 fp32、batch 1。沒量 GPU 批次推論、多執行緒、量化。
- benchmark 是只保留必要部分的重寫，不是 run.c 本身；S-merged 照抄 run.c:244-255 的迴圈。P 沒有對應的 run.c。
- 42M 的一次掃完寫法兩次都特別慢（對 S-merged，S 約 1.18 倍、P-free 約 1.6 倍），原因沒查；取最快寫法的比較不受影響。
